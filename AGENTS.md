## Learned User Preferences

- Day-to-day work goes on the `develop` branch; the repo keeps only `main` and `develop`. Commit/push to `develop`, then merge to `main` for releases.
- Plan-first workflow: produce a written plan file, then execute it with the prompt "Implement the plan as specified, it is attached for your reference. Do NOT edit the plan file itself." Do not regenerate todos that the plan already created.
- After substantive UI/app changes, always finish by deploying with `npm run deploy:preview` and reply with the Hosting channel URL (the `…--preview-…web.app` link), not just the default site URL. Resend pre-assessment links use production `APP_HOST` (default `*.web.app`), not preview channels — run production hosting deploy when validating `/remote` for real clients.
- UI taste is minimalist and Claude-inspired: **clarity over cleverness** — the next move should always be obvious; push back on busy or “clever” UI. No boxes-in-boxes, no overlay paragraphs, restrained rounding, pill-shaped quick actions, full-bleed work surfaces. Computer-vision overlays (MediaPipe pose landmarks, etc.) must feel professional and trustworthy — restrained dot size and thin lines, never the heavy default look. **Client AXIS report** must be **presentable for a live post-assessment debrief**: professionally presented (InBody-like document feel), scannable, no placeholders or walls of text; **goal-first** (findings secondary to the client’s stated goals — show we can get them there); path forward as a concrete **3-phase plan** tied to those goals; optional simple roadmap if they don’t continue. Drop decorative pillar graphics (body-comp bars, muscle maps, metabolic icons); hero radar optional/minimal; posture photos once in an elegant filmstrip with clear findings (not duplicated in Movement). **Lifestyle** uses the icon status grid (`LifestyleFactorsCard`, green/amber/red per factor) — not gap tables or long prose. **Movement** tells findings visually/concisely — not gap analysis. Measurable pillars can use current / 4-month / 12-month gap tables with goal-prioritized realistic progress. Report hero is **goal chips + "where to focus first"** — the score ring is demoted, never dominant. A **"Your 90-day roadmap"** section (between hero and path forward) shows one deterministic behaviour card per assessed pillar — framework-level behaviours only, **never sets/reps**, no AI call, ~1.5× a pillar section tall. The **self-guided takeaway** for non-signups is a compact 3-bullet habit block under the coached plan — never a second full plan. **Do not reference ARC** in the client report for now. Empty client surfaces must not show archetype or pillar scores before real assessment data. Healthy metrics outside the client’s goals should be congratulated or lightly maintained — not pushed to elite performance targets. Client/PWA copy stays plain-language (**Fitness level**, not raw VO₂/HRR). Coach daily loop: assess → AXIS report → pillar reassess → milestones → shareable artifacts; push back on duplicate surfaces and assessment pre-flight complexity. Remote pre-assessment welcome: one **Start** CTA, duration hint in brackets under the button, two short motivating lines — no numbered step lists or boxy landing chrome. Live movement capture on iPad: **observe-then-tag** chip pads (large targets, optional “looks good”, summary after the set) — not stacked dropdowns while the client is mid-rep.
- **New-client baseline:** **Pre-assessment** (P0 PAR-Q + P1 lifestyle/goals + optional posture) via coach link or in-studio; **physical assessment** in app (**P3 → P5 → P4 → P2 → P7**, `STUDIO_PHYSICAL_PHASE_ORDER` — fitness first for a true seated resting HR; within P4 movement patterns come before posture photos so photos → tape → analyzer form one station block). No in-app consultation product or booking funnel — consultations happen outside One Assess. **Walk-in studio:** P0/P1 in studio → physical order above. **Send link first:** client completes pre-assessment at home → studio shows **pre-assessment review only if partial** → physical (skip P0/P1 when remote complete; skip duplicate studio posture if four remote views set). **Entry flow:** every global "New assessment" button is new-client-only (client info → straight into first capture step); existing-client reassessments — full or the more common partial — start from the client profile, never the global buttons. Goals (`clientGoals`, `trainingFrequency`, `goalDeadline`) live on P1 + remote `full` scope. Legacy `consultations` subcollection is read-only. Full plan is `buildStudioBaselinePlan()` (no P6); plan-wizard templates only after first completed full assessment; pre-assessment links via Resend (`emailRemoteIntakeLink`), never `mailto:`.
- Light/dark contrast is checked aggressively — avoid volt-green (brand) text on white/light backgrounds; every component must stay legible in both themes.
- Treat the user as a CLI/Firebase novice: when shell or migration steps are involved, walk through one command at a time, explain what each path/credential is, and do not assume placeholders will be resolved.
- For chat "thinking" UX, show short ephemeral status lines with loading dots (e.g., "Fetching X…", "Putting together a table…") that disappear before the final answer — never leave a residual list of steps in the message.
- Branding/copy must be wired through a single source so updates (PWA install prompt, notification bell, favicon, share artifacts, emails, landing page) propagate everywhere from one change.
- Prefer deterministic data-fetch flows over LLM calls whenever possible to control AI cost; lazy-inject only the client/assessment data the turn needs and cap conversation history.
- When a fix doesn't land after a couple of attempts, do a deep dive of the official docs (Context7 / vendor docs) before trying more variations.
- Assistant page is chat-first: top tabs Chat / Work / Clients; chat box centred when starting a new chat and drops to the bottom with a `+` quick-actions menu in an active chat; user profile bottom-anchored in the side panel; AI usage meter shows only at ≤50% remaining; "Artifacts" (Reports / Roadmaps / Achievements) are social-formatted shareables that open as centred modal pop-ups from the side panel — never as a separate page.

## Learned Workspace Facts

- Stack: React 18 + Vite + TypeScript + Tailwind + shadcn/ui + Firebase (Firestore, Functions, Hosting, App Hosting) + MediaPipe + TanStack Query + Recharts. `.cursorrules` forbids `console.log` in committed code — always use the logger at `src/lib/utils/logger`. Root `tsconfig.json` is a solution file, so plain `tsc --noEmit` checks nothing — use `tsc --noEmit -p tsconfig.app.json`; vitest must exclude compiled `functions/lib/**`.
- User-facing brand is "One Assess" (the repo is `fitness-flow-form`); app is region- and currency-agnostic — GBP is the base, users transact in their local currency via Stripe + Wise multi-currency, the admin dashboard normalises to GBP with optional per-region drill-downs, and there must be no device-specific copy (no "iPhone", no "InBody").
- Brand vocabulary is user-facing only — never rename internal variables, Firestore fields, or scoring logic:
  - **AXIS Score™** (client-facing) = overall 0–100 rolling up five pillars. Client report v2 (`buildClientReportModel`, `ClientReportV2Layout`): **goal-first** hero (goal chips + "where to focus first"; score ring demoted) → **90-day roadmap** (deterministic per-pillar behaviour cards, `clientRoadmapCards.ts`, goal-priority order) → **Your path forward** (concrete 3-phase plan with real 4/12-month projection figures; compact 3-bullet **self-guided takeaway** underneath for non-signups) → **Posture filmstrip** when captures exist (clear findings; not repeated in Movement) → **Pillar briefs** (measurable pillars may show current / 4-month / 12-month gap tables with goal-prioritized progress; no decorative graphics) → **Lifestyle** icon status grid (`LifestyleFactorsCard`) → **Movement** findings (not gap tables); single-scroll; **no ARC teaser/references for now**. The post-save **coach debrief renders the exact same v2 document** the client sees; the public `/demo` marketing page intentionally keeps the legacy layout. Re-opens from saved `formData`/scores with **original assessment dates**; posture overlay images refresh only on **re-capture** or backfill. Cardio client line uses plain-language **Fitness level** (`calculateCardioAnalysis` — fixed inverted-HR submax inflation). Copy in `src/constants/clientReport.ts`.
  - **SIGNAL™ Report** (coach-facing only) = cross-pillar synthesis layer (priority themes, urgency, "what it means"); never surface in the client AXIS report.
  - **ARC™** (client-facing) = journey/roadmap with phases Foundation → Development → Performance; the system pre-fills a suggested ARC from the first full assessment's AXIS findings + client goals, the coach edits/confirms before sending; subsequent pillar assessments auto-update milestones; ARC completes when goals are hit, after which the next full assessment opens new goals — keep ARC off the AXIS report until explicitly re-enabled.
- **Assessments:** first baseline uses `buildStudioBaselinePlan()` (P0,P1,P3,P5,P4,P2,P7 — no P6) via `NewClientModal` (studio now or `remoteScope: 'full'` pre-assessment link). Coach sidebar groups **Pre-assessment** (P0,P1) vs **Physical assessment** (P2–P5,P7). `shouldShowStudioIntakeReview()` gates optional partial pre-assessment review only. Remote `/remote/:token` is mobile-first (one question per screen, choice cards not clipped selects); body comp in-studio (OCR must fail soft into fast manual entry — scan friction is a known studio pain). Body comp "Snap a Photo" opens the device camera **directly on every device** (the QR phone-companion modal is removed from body comp — routing tablets to it was the "scanner stopped working" regression); OCR apply never auto-advances, bad reads offer retake-or-manual, and kill-switch/credit blocks get distinct messaging. **Fitness (P3) is one flow**: resting HR is the first input of the section, run timers via `CardioRunSheet`. Draft recovery keys on the saved **phase ID**, not index position, so phase reordering can't corrupt drafts. Remote submit sets `remoteIntakeAwaitingStudio`; overview CTA → start/continue physical assessment. `trainingFrequency` / `primaryTrainingStyles` only when `recentActivity === 'currently-training'`. **Movement:** P4 uses chip capture (`MovementPatternCapture`) for OHS/hinge/lunge; mobility sub-score derived via `deriveMobilityFromPatterns.ts` when legacy mobility fields empty (detail line: "Inferred from movement"; blank pattern fields mean **not observed**, never "good" — an empty form must not score 100); standalone mobility section removed from P4. Partial posture pillar mini-run defaults to posture section only. AXIS report **projected outlook** uses **4 / 12 month** (and related) horizons from baseline + `clientGoals`, extrapolated at goal-prioritized realistic rates (e.g. stated weekly loss/gain), not overly conservative under-projections. After first full assessment, modular reassess uses wizard/queue; overall AXIS Score™ only on full completion. Emailed intake URLs use Functions `APP_HOST` (production hosting); stale PWA/browser/iPad cache can show old UI until hard refresh.
- AI assistant has two modes the user toggles between: a deterministic "data" mode (fetch-and-report from Firestore only, no hallucination) and a free LLM mode for general fitness/programming questions.
- Strict multi-tenancy: coaches see only their own clients; org admins get top-level org metrics (counts, capacity, coach activity) but never another coach's client-specific data. `coachUidFilter: null` = full org scope (admin & non-coaching admin); `coachUidFilter: undefined | uid` = own clients only — Firestore rules mirror this. Public client routes (`/r/:token`) are air-gapped from coach PII via dedicated `PublicReportViewer` / `PublicRoadmapViewer` components that read only public-safe paths.
- Posture: in-studio offers two visible options — **coach-held live capture** on the assessment device (`CoachPostureCapturePanel` + `PostureGuideOverlay` alignment guides for head/toes/vertical midline; UI prompts each view in order, coach shoots, judges quality, confirms or retakes; no voice/position detection) or the QR mobile handoff; DIY remote capture unchanged. Gemini Live (`gemini-3.1-flash-live-preview`) remains the only voice when voice mode is used. `window.speechSynthesis` (Apple/browser TTS) must be hard-blocked in posture mode via `disableSpeechSynthesis: true` and `suppressAudioFeedback: true`. Live API is gated behind `VITE_ENABLE_GEMINI_LIVE`; voice configurable via `VITE_GEMINI_LIVE_VOICE_NAME`. When voice mode is on, walk the client through purpose → framing → per-pose countdown → close-out in plain language. Framing should stay comparable across sessions. Client photo uploads in HEIC/HEIF are converted server-side (Cloud Function) when browser conversion fails.
- Body-comp OCR uses `gemini-2.5-flash` via VertexAIBackend; OCR pipeline is a straight-through `preCropImage → runGeminiOcr → validate → return`, with no learned-pattern Firestore caching.
- Server-only operations (PDF, email/Resend, billing/Stripe, admin) live in Cloud Functions; when `firestore.rules`, any Cloud Function, or `executeClientErasure.ts` paired with `OrgOverview.tsx` change, deploy via `firebase deploy` — never hosting-only `deploy-preview.sh` for those.
- Client PWA shell direction: three bottom tabs — AXIS report (assessment snapshot + history), ARC (journey across assessments), Milestones (achievements). In-report navigation is vertical scroll with optional pillar jump row, not five pillar tabs.
- **Client delete:** Manage → Delete permanently requires typing the exact profile display name (title-cased `displayClientName`), not the URL slug — common after remote intake updates the name. Clients table bulk Delete = soft delete (30-day Trash). `remoteIntakeAwaitingStudio` does not block deletion. Dashboard Active/Today must honor client doc `status`; soft delete clears intake flags so deleted clients don't ghost on Today.
- Append-only analytics: every entity that contributes to analytics writes pre-computed summaries (`scoresSummary`, `categoryScores`, `pillarBreakdown`) at write time; new indexes go into `firestore.indexes.json` in the same PR.
